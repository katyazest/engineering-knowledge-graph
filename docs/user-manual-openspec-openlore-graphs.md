# Руководство пользователя: работа с OpenSpec-графом и OpenLore-графом

## Для кого это руководство

Это руководство предназначено для аналитика, владельца требований или другого участника команды, которому нужно быстро разобраться в задаче, требованиях и связанных сервисах без ручного просмотра всех репозиториев.

Инструмент помогает отвечать на вопросы вида:

- какие требования относятся к задаче;
- какие OpenSpec-изменения затрагивают нужную область;
- какие сервисы связаны с требованиями;
- где в коде можно проверить реализацию;
- где заканчивается контекст требований и начинается контекст кода.

## Главная идея

В рабочей папке проекта есть два локальных графа:

- `.engineering-kg/` - граф проектного и смыслового контекста: требования, OpenSpec-изменения, спецификации, сервисы и связи между ними;
- `.openlore/` - граф структуры кода: репозитории, файлы, модули, классы, функции и другие элементы реализации.

Они дополняют друг друга, но не заменяют друг друга.

```text
                    WORKSPACE
                       │
        ┌──────────────┴──────────────┐
        │                             │
.engineering-kg/                  .openlore/
        │                             │
        ▼                             ▼
    EKG MCP                      OpenLore MCP
        │                             │
 semantic/project                 code structure
    context                         context
        ▲                             ▲
        │                             │
 ┌──────┴───────┐             ┌───────┴───────┐
 │              │             │               │
requirements  service-A    service-A       service-B
  agent        agent        agent           agent
```

Простыми словами:

- EKG MCP отвечает на вопросы о требованиях, OpenSpec, спецификациях, сервисах и трассируемости.
- OpenLore MCP отвечает на вопросы о коде и структуре сервисов.
- Агент по требованиям сначала смотрит в EKG MCP.
- Агент по конкретному сервису может использовать и EKG MCP, и OpenLore MCP, но не должен смешивать логику разных сервисов.

## Что такое EKG MCP

EKG MCP - это локальный помощник для запросов к Engineering Knowledge Graph.

Он показывает не полный текст всех документов, а компактные проверяемые факты:

- список требований;
- список сервисов;
- список OpenSpec-изменений;
- связи между изменениями, требованиями, спецификациями и сервисами;
- ссылки на источники, где факт можно проверить.

EKG MCP нужен, чтобы понять смысловую карту проекта: что меняется, зачем, где это описано и какие части проекта затронуты.

## Что такое OpenLore MCP

OpenLore MCP - это локальный помощник для анализа структуры кода.

Он нужен, когда уже понятно, какой сервис или репозиторий нужно проверить. Через него можно уточнять:

- где находится нужный модуль;
- какие файлы и символы связаны с областью изменения;
- какая структура у конкретного сервиса;
- какие участки кода стоит проверить как evidence.

OpenLore MCP не должен использоваться как источник бизнес-требований. Он помогает понять реализацию, а не заменить требования.

## Типовой сценарий работы

### Сценарий: нужно разобраться с новой задачей

Представим, что в Jira появилась задача: изменить поведение платежей.

Пользователь хочет понять:

- есть ли OpenSpec-изменение по этой задаче;
- какие требования оно добавляет или меняет;
- какие спецификации затронуты;
- какой сервис отвечает за реализацию;
- где в коде искать подтверждение.

### Шаг 1. Открыть проектный workspace

Сначала агент работает не с одним репозиторием, а с общей рабочей папкой проекта.

В ней обычно лежат:

```text
project-directory/
├── .engineering-kg/
├── .openlore/
├── openspec/requirements_repo/
└── src/codebase_repos/
```

Для пользователя важно только правило: графы лежат на уровне workspace, а не внутри отдельного сервиса.

### Шаг 2. Спросить EKG MCP о требованиях и изменениях

На этом шаге агент обращается к EKG MCP.

Примеры пользовательских вопросов:

- "Покажи OpenSpec-изменения по платежам."
- "Какие требования связаны с capability payments?"
- "Какие спецификации затрагивает изменение JIRA-123?"
- "Есть ли трассировка от изменения к durable specification?"

EKG MCP возвращает список найденных объектов и связей. Если связи нет, он должен явно показать отсутствие связи, а не придумывать ее.

### Шаг 3. Определить затронутый сервис

После запроса к EKG MCP агент может увидеть, что требование связано, например, с сервисом `service-A`.

Это важная граница:

- если требование относится к `service-A`, агент не должен автоматически переносить эту логику на `service-B`;
- если связь с `service-B` не указана в графе, ее нужно проверить отдельно;
- если связь отсутствует, это может быть пробелом в требованиях или в графе.

### Шаг 4. Перейти к OpenLore MCP только для нужного сервиса

Когда сервис определен, агент обращается к OpenLore MCP.

Примеры пользовательских вопросов:

- "Покажи структуру `service-A`, связанную с платежами."
- "Где в `service-A` находится обработчик операции оплаты?"
- "Какие файлы стоит проверить для реализации этого требования?"

OpenLore MCP помогает найти кодовые места, но не должен менять смысл требования. Если код делает одно, а OpenSpec говорит другое, это не повод переписать требование по коду. Это повод зафиксировать расхождение.

### Шаг 5. Сверить требования и код

После двух запросов у пользователя есть две части картины:

- из EKG MCP: что должно быть по требованиям и OpenSpec;
- из OpenLore MCP: где это может быть реализовано в коде.

Дальше агент может подготовить вывод:

- требование найдено;
- изменение найдено;
- затронута спецификация;
- связан сервис `service-A`;
- в коде есть такие-то места для проверки;
- для `service-B` связи не найдены, поэтому переносить вывод на него нельзя.

## Пример правильного использования

Пользователь спрашивает:

> Нужно понять, что затрагивает задача JIRA-123 по возвратам.

Правильный порядок:

1. Спросить EKG MCP о change `JIRA-123`.
2. Получить связанные requirements и touched specs.
3. Проверить traceability к durable specs.
4. Определить связанные сервисы.
5. Для каждого связанного сервиса отдельно спросить OpenLore MCP о кодовой структуре.
6. Сформировать ответ с разделением: требования, спецификации, сервисы, кодовые evidence.

Неправильный порядок:

1. Сразу искать по всем сервисам в коде.
2. Смешивать найденную реализацию из `service-A` и `service-B`.
3. Делать вывод, что требование относится к сервису, если такой связи нет в EKG.
4. Считать код источником целевого поведения вместо OpenSpec.

## Какие вопросы задавать EKG MCP

Для начального анализа:

- "Какие есть OpenSpec-изменения?"
- "Какие изменения активные, а какие архивные?"
- "Какие требования относятся к capability `<название>`?"
- "Какие сервисы есть в графе?"

Для трассировки:

- "Покажи traceability для этого требования."
- "Покажи traceability для этого OpenSpec-изменения."
- "Есть ли связь изменения с durable specification?"
- "Какие touched specs есть у изменения?"

Для проверки границ:

- "С какими сервисами связано это требование?"
- "Есть ли связь с `service-B`?"
- "Какие факты подтверждают связь?"

## Какие вопросы задавать OpenLore MCP

OpenLore MCP лучше использовать после того, как EKG MCP уже сузил область поиска.

Хорошие вопросы:

- "Покажи структуру репозитория `service-A`."
- "Найди файлы, связанные с операцией возврата."
- "Покажи символы, связанные с обработкой платежа."
- "Где находится реализация API-операции?"

Менее надежные вопросы:

- "Как должно работать требование?"
- "Какой сервис отвечает за бизнес-процесс?"
- "Какие требования нужно написать?"

Такие вопросы лучше сначала задавать EKG MCP или проверять в requirements repository.

## Что делать, если граф не нашел связь

Отсутствие связи не означает автоматически, что связи нет в реальности.

Возможные причины:

- связь еще не описана в OpenSpec;
- graph store не был пересобран после изменений;
- capability назван иначе;
- задача относится к другому сервису;
- в требованиях есть пробел.

В этом случае правильный вывод должен звучать осторожно:

> В EKG-графе связь не найдена. Нужно проверить OpenSpec-изменение, durable specification или обновить граф.

## Что нельзя делать

Нельзя:

- хранить в графе токены, пароли, ключи и приватные данные;
- считать OpenLore источником требований;
- переносить логику одного сервиса на другой без явной связи;
- делать выводы только по названию файла или похожему имени;
- считать отсутствие результата окончательным доказательством без проверки актуальности графа;
- копировать в EKG полный исходный код, тела функций, payload Jira, Bitbucket или Confluence.

## Короткая памятка

Используйте EKG MCP, когда вопрос про смысл:

- требования;
- OpenSpec;
- спецификации;
- изменения;
- сервисные границы;
- трассируемость.

Используйте OpenLore MCP, когда вопрос про код:

- файлы;
- модули;
- классы;
- функции;
- структуру репозитория;
- места для проверки реализации.

Рабочий порядок:

1. Сначала EKG MCP.
2. Потом OpenLore MCP для конкретного сервиса.
3. Затем сверка требований и кода.
4. В выводе явно разделять: что известно из требований, что найдено в коде, какие связи отсутствуют.
